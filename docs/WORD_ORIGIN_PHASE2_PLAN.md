# 単語語源 段階2: 語根バッチでデータを投入する

対象: `data/word_origins.json` / `scripts/check-word-origin-data.cjs`
関連: [WORD_ORIGIN_PLAN.md](WORD_ORIGIN_PLAN.md)（全体計画）/ [WORD_ORIGIN_PHASE1_PLAN.md](WORD_ORIGIN_PHASE1_PLAN.md)（辞書の確定）/ [WORD_ORIGIN_AUTHORING.md](WORD_ORIGIN_AUTHORING.md)（作成基準）
前提: 段階0＝`baf6fd4`（仕組み一式）、段階1＝`db3bdee`（語根20・接辞20の辞書）
状態: 完了（2026-08-25）

## 0. この段階のかたち

`data/word_roots.json` の語根20個について、`scripts/build_word_origin_stub.py` が出す候補を1語ずつ判定し、A型を `data/word_origins.json` に入れる。**1バッチ＝語根2〜4個＝1コミット**。

候補の総数は**138語**（`voc` の4語を含む。段階0で2語登録済み）。ここからA型として残るのは**100語前後**の見込み。

## 1. バッチ編成

`--root` に渡す語根と、スタブが出す候補数（実測）。

| バッチ | 語根 | 候補数 | 狙い |
| --- | --- | --- | --- |
| 1 | `spec`(11) / `pos`(15) / `vert`(12) | 38 | 最大の塊。ここで仲間語パネルが3語ローテーションで動く状態になる |
| 2 | `fer`(9) / `port`(7) / `luc`(10) | 26 | 「運ぶ」2語根が並ぶので、訳の書き分けを固める |
| 3 | `lect`(11) / `cap`(9) | 20 | 同綴異根の判定が最も難しい2つ。バッチを小さくする |
| 4 | `duc`(5) / `gress`(5) / `ven`(7) / `ced`(6) | 23 | 素直な語根をまとめて消化 |
| 5 | `scrib`(4) / `nunc`(4) / `quir`(4) / `voc`(4) | 16 | `voc` は段階0の2語に `evoke` `revoke` を足して完成させる |
| 6 | `tract`(3) / `plac`(4) / `cid`(4) / `lev`(4) | 15 | 残り |

難しい語根（3）を早い順番に置き、判定基準が固まらないまま量を稼がないようにする。

## 2. 候補は4つに分ける（3分類ではない）

スタブの候補は**綴りの部分一致**なので、`WORD_ORIGIN_AUTHORING.md` のA/B/Cに入る前に「そもそもその語根ではない」語が混ざる。判定は次の4つ。

| 判定 | 意味 | 扱い |
| --- | --- | --- |
| 対象外 | 綴りが一致しただけで、その語根と無関係（`lucrative` `escape` `deflect` など） | **何も記録しない**。記録し始めると際限がない |
| A | その語根を実際に含み、分解が中心義を思い出す助けになる | `word_origins.json` に登録 |
| B | 語根は含むが分解が効かない／別語源の由来話が有効 | `derivation` のみで登録 |
| C | その語根を実際に含むが、分解するとこじつけになる | `cReasons` に語根名つきで理由を1行 |

**対象外とCの線引き**が要点。「無関係だから外す」のは記録不要、「関係はあるが説明にならないから外す」のがCで、これは後から同じ語を再検討しないために記録する。判断に迷う語は対象外ではなくCに寄せる。

同綴異根の具体例は `word_roots.json` の各 `note` にある。バッチ開始時に対象語根の `note` を読む。

## 3. 1バッチの手順

1. `python scripts/build_word_origin_stub.py --root <語根>` を語根ごとに実行する。
2. 候補を4分類する。A型は `parts`（接頭辞→語根→接尾辞の順）と `derivation` を書く。
3. 新しい接辞が必要になったら `word_roots.json` の `affixes` に**独立エントリ**として足す（異形は `variants` にまとめない。段階1の方針）。同じバッチのコミットに含める。
4. `npm test`。`derivation` の末尾が `meaning` の中心義と結び付かない語は落ちるので、書き直すかB・Cへ移す。
5. ブラウザでそのバッチの単語カードを1枚開き、チップ・導出行・仲間語パネル・375px幅を確認する。
6. 1バッチ＝1コミット（例: 「語根 spec・pos・vert の語源を追加する」）。

## 4. 検査に足すもの

バッチ1に着手する前に入れる。

- **`parts[].form` の接辞が `affixes` に存在すること**（段階1で見送った項目）。これを入れると、辞書に無い接辞を勝手に使えなくなり、接辞の訳がカード間で揺れなくなる。現行3語の `equi` `ate` `e` `ative` は登録済みなので、そのまま通る。
- **同じ `root` のA型が2語以上あるとき、逆引きが空にならないこと**。仲間語パネルが出るかどうかをデータ側で機械的に担保する。
- `cReasons` は語根名を添えた形に整える（`["lucrative", "luc: 利益のlucrum系で、光の語根ではない"]` のように、なぜその語根の検討で外したのかが後から分かるようにする）。

**入れないもの**: 「登録件数が n 件以上」という下限。件数の消化を目的にしないという方針（`WORD_ORIGIN_AUTHORING.md`）に反するため、段階1で入れた `origins >= 3` 以上には上げない。

## 5. 執筆時の注意

- **循環を書かない**。`parts[].gloss` は構成要素自身の意味であって、単語の訳ではない。
- **接辞の意味を選ぶ**。`in` / `im` は「中へ」と「否定」の2義があるので、その語でどちらなのかを `parts[].gloss` に書く（辞書の `gloss` をそのまま貼らない）。
- **`derivation` は1行**。矢印の後ろは `vocab_*.json` の `meaning` の中心義に合わせる。複数セットに同じ語があるときは、どれか1つの `meaning` と結び付けば検査は通るが、**意味が違うセットがある語は要注意**（`accept` のように訳が2通りある語）。
- **`parts` は2〜4個**に収める。接頭辞・語根・接尾辞で足りる。細かく割りすぎるとカードが読めない。
- 段階1の `note` で「含めない」と書いた語を、後から別バッチでうっかり入れない。

## 6. 完了条件

- 20語根すべてについてバッチが完了し、各候補が4分類のいずれかに落ちている。
- `npm test` が通る。4章の検査2件が追加されている。
- `spec` `pos` `vert` のような10語超の語根で、カードごとに違う仲間語3語が出る（ローテーションが実際に効いていることをブラウザで確認）。
- `data/word_roots.json` の20語根のうち、A型が0語のままの語根が無い（0語なら語根選定が誤っていたということなので、辞書から外すか候補を見直す）。

## 7. 非目標

- 20語根の外への拡張。次の語根群は段階3として別に計画する。
- 1183語の全カバー。この段階で触れるのは候補138語だけで、残る1000語超は語源表示を持たない状態が正常。
- 熟語側（`coreImage`）への波及。

## 8. 段階3の入口（この計画の外）

段階2が終わったら、次のどちらを先にやるか決める。

1. **語根を増やす**: 段階1で見送った候補（`ver` `nat` `her` `min` `cord` `aud` など）の再精査ではなく、`fac` `dic` `sens` `gen` `form` `fin` など未検討の語根群を新たに粗一致にかける。
2. **B型を増やす**: 語根を持たない借用語（`liaison` `graft` `rapport` など）の由来一行を、頻出語から拾う。カバー率は上がるが仲間語パネルは出ない。

学習効果は1が高いが、A型が100語前後で頭打ちになった時点で、2に切り替える判断もある。
