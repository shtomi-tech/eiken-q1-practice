# 単語語源 段階5: 単発の語根を解禁してカバー率を上げる

対象: `data/word_roots.json` / `data/word_origins.json` / `static/mode-q1.js` / `scripts/check-word-origin-ui.cjs` / `docs/WORD_ORIGIN_AUTHORING.md`
関連: [WORD_ORIGIN_PHASE1_PLAN.md](WORD_ORIGIN_PHASE1_PLAN.md)（語根の要件を決めた回）/ [WORD_ORIGIN_PHASE4_PLAN.md](WORD_ORIGIN_PHASE4_PLAN.md)（級横断化）
前提: 段階4＝`bcfb4c0`（語根33個・A型136語・B型18語・カバー率13.0%）
状態: バッチ0実装済み（2026-08-25、未コミット）。仲間語0でも語根パネルを表示し、接頭辞候補スタブと単発語根の作成基準を追加。

## 0. 方針変更

段階1で「語根は複数語で使えるものだけを登録する」と決めた。この制限を**外す**。

理由は測定にある。未カバー1029語のうち、**登録済みの接辞が付く語が468語**（接頭辞281／接尾辞314／両方127）ある。これらが漏れていたのは分解できないからではなく、**語根が1〜2語にしか出てこないから**だった。

```
invigorate   in（中へ）＋ vigor（活力）        → 活力を入れる
precocious   pre（前もって）＋ coc（煮る）      → 早く熟した
incarcerate  in（中へ）＋ carcer（牢屋）＋ -ate → 牢屋へ入れる
incumbent    in（上に）＋ cumb（横たわる）      → 職に就いている
```

`vigor` `coc` `carcer` `cumb` はアプリの語彙では1語ずつしか使わないが、**分解して中心義を導けるという要件は満たしている**。段階1の制限は「仲間語パネルを出せること」を語根の要件と混同していた。

新しい要件は1つだけにする。

> その語根を示すことで、学習者がその単語の中心義を思い出せること。仲間語が何語あるかは問わない。

見込みは**カバー率13% → 30〜40%**。段階5では上位6接頭辞（約170語候補）を扱い、残りは段階6に回す。

## 1. UI変更: 仲間語が0でも語根パネルを出す

現在は仲間語が0語だとパネルごと非表示になる（`flashWordOrigin` の `if (visibleSiblings.length)`）。単発語根の語が250語規模で入ると、**その全カードで語根の出典が見えない**ことになる。

パネルの表示条件を「語根辞書にエントリがあること」に変える。

```
語根「carcer」＝牢屋（ラテン語 carcer）
牢屋に閉じ込めるイメージ。incarceration も同じ語根。
（仲間語リストは、アプリ内に仲間語があるときだけ出す）
```

- 仲間語リスト（`.particleSiblings`）は今までどおり1語以上あるときだけ描く。
- `check-word-origin-ui.cjs` の該当アサーションを、この条件に合わせて更新する。
- CSSの変更は不要。

## 2. バッチは接頭辞単位で切る

単発語根なので語根単位ではまとめられない。**接頭辞単位**にすると、同じ接頭辞の意味の当て方（段階2で問題になった多義の選択）を1バッチ内で揃えられる。

未カバー語を接頭辞で分けた実数は次のとおり（括弧内は接尾辞も付く語数）。

| バッチ | 接頭辞 | 候補 | 段階5の扱い |
| --- | --- | --- | --- |
| 1 | `in-` | 45（24） | ○ |
| 2 | `re-` | 38（15） | ○ |
| 3 | `de-` | 31（15） | ○ |
| 4 | `con-` | 21（11） | ○ |
| 5 | `dis-` | 18（5） | ○ |
| 6 | `ex-` | 15（9） | ○ |
| — | `en-` 13 / `im-` 13 / `pro-` 10 / `com-` 9 / `per-` 8 / `pre-` 8 / `co-` 7 / `ac-` 6 | 74 | 段階6 |
| — | 接頭辞なし・接尾辞のみ | 187 | 段階6 |

段階5の候補は**168語**。`in place` `income` `increase` `deadline` `deadlock` `engine` のような偽陽性が2〜3割含まれるので、**A型として残るのは100〜120語**の見込み。終了時点でカバー率は**21%前後**になる。

## 3. 品質ガード（単発語根はここが要）

仲間語で相互検証できないぶん、1語ごとの正しさが担保しにくい。次の3点を `WORD_ORIGIN_AUTHORING.md` に足す。

1. **語根の `origin` にラテン語・ギリシャ語の原形を必ず書く**（既存の必須項目）。原形が書けない語根は登録しない。
2. **語根の `note` に、その語根を持つ英語の別の語を1つ以上挙げる**（アプリ未収録でよい）。`carcer` なら `incarceration`、`cumb` なら `succumb`。実在性の担保になり、1章の変更でカードにも表示される。
3. **迷ったらB型**。「pre＋coc」のように分解が中心義に直結する語だけをA型にし、分解しても意味が出てこない語は由来一行のB型にする。件数を目的にしない方針は変えない。

段階2で作った4分類（対象外 / A / B / C）と `cReasons` の運用はそのまま続ける。

## 4. 検査

- `check-word-origin-ui.cjs`: パネルの表示条件の変更に追随（1章）。
- `check-word-origin-data.cjs`: **変更しない**。単発語根は既存の「A型が2語以上ある語根だけ逆引きを検査する」条件をそのまま素通りする。語根数や件数の下限は増やさない。
- 進捗表示として、`A型が1語しかない語根の数`を検査の最後にログ出力する（`core image progress:` と同じ流儀）。増えすぎたら方針を見直す材料にする。

## 5. 手順（1バッチ）

1. 対象接頭辞で未カバー語を抽出する（`build_word_origin_stub.py` は語根単位なので、`--prefix` オプションを足す）。
2. 4分類する。A型は語根を `word_roots.json` に足しつつ `word_origins.json` に登録する。`gloss`（16文字以内・`meaning` の部分文字列）も同時に入れる。
3. `npm test`。
4. ブラウザで、そのバッチの語を1枚と、**仲間語0のカード**を1枚確認する（パネルが出ること）。375px幅も見る。
5. 1バッチ＝1コミット。

## 6. 合格条件

- 段階5終了時点でA型が240語前後、カバー率21%前後になる。
- 仲間語0のカードで語根パネルが出る（1章）。
- すべての新規語根に `origin` と、別の英単語を挙げた `note` がある（3章）。
- `npm test` が通り、既存136語の表示が変わらない。

## 7. 非目標

- 468語すべてを段階5で終えること（段階6に回す）。
- 接尾辞だけが付く187語（段階6で、語根が英語として不透明なものはB型に寄せる方針を別途決める）。
- 語根に仲間語を無理に増やすこと。単発語根は単発のままでよい。
